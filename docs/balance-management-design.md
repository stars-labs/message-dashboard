# SIM 余额管理设计与实施规范

## 1. 目标

余额能力需要从“短信列表中的一类特殊会话”升级为可日常操作的独立模块，同时保留查询短信的完整审计链路。

本期交付统一覆盖三个入口：

1. 消息页通过 `验证码 / 余额查询 / 全部短信` 三段控件切换内容。
2. 独立的“余额”模块用于浏览所有 SIM 的余额健康状态和查询记录。
3. “设备与卡”列表显示最近余额，但不承担余额管理工作流。

充值仍属于后续阶段。本期不提供没有后端权限、幂等和审计保障的充值按钮。

## 2. 信息架构

### 2.1 主导航

- 桌面端主导航：`消息 / 设备与卡 / 余额 / 规则 / 用户`。
- 手机端底部导航：`验证码 / 设备 / 余额 / 发送 / 更多`。
- 余额使用钱包图标，与设备模块和发送模块在视觉上可明确区分。

余额模块内部提供两个视图：

- `余额概览`：一张 SIM 一行，回答“哪些卡需要处理”。
- `查询记录`：一次查询一行，回答“余额是如何得到的”。

### 2.2 消息页

消息页使用可见的三段控件，不使用下拉菜单：

- `验证码`：只显示识别出验证码的普通短信。
- `余额查询`：只显示按查询编号分组的余额查询会话。
- `全部短信`：普通短信和余额查询会话按时间混排。

垃圾短信开关只在“全部短信”中出现。余额查询短信由查询编号归组，不以普通散装短信重复展示。

## 3. 余额概览

### 3.1 摘要指标

页面顶部只显示数量，不跨币种合计金额：

- 正常
- 需要充值
- 数据过期
- 查询失败
- 尚未取得

不同货币不可相加。未来需要资产汇总时，应按 `CNY / SGD / HKD` 分组展示。

### 3.2 列表字段

桌面端字段：

| 字段 | 内容 |
| --- | --- |
| SIM | `S01` 格式卡号、手机号、ICCID |
| 运营商 | 国家/地区和运营商 |
| 当前余额 | 金额与币种；无结果时显示“暂未取得” |
| 状态 | 正常、需要充值、数据过期、查询失败、尚未取得 |
| 阈值 | 该卡对应的充值阈值 |
| 最近更新 | 最近一次成功取得余额的时间 |
| 最近查询 | 查询状态与查询方式 |
| 操作 | 有查询记录时可查看详情 |

手机端使用紧凑的全宽列表行，不使用横向滚动表格。第一行展示卡号、号码和状态，第二行展示余额、运营商和更新时间。

### 3.3 查询操作

查询操作仅授予管理员的 `balances.query` 权限，浏览器不接触守护进程使用的 `API_KEY`。

- 单卡查询：每一行提供“查询”按钮。服务端自动选择匹配的运营商配置，验证卡在线状态并执行 24 小时防重复，然后创建可审计的查询和发送队列记录。
- 批量查询：页面先请求服务端预览，分别展示可查询、24 小时内已查询、离线、未支持和尚未完成验证的数量；确认后由服务端统一入队，浏览器不循环调用单卡接口。
- 正式启用的运营商配置可以覆盖所有匹配 SIM。发现模式配置只允许单卡查询；批量查询仅包含该配置下已有成功解析记录的 SIM。
- 守护进程每轮最多领取 5 条余额维护短信，普通用户短信优先，避免批量查询占满发送队列。

操作完成后页面刷新查询记录，并通过现有状态展示 `排队中 / 等待回复 / 已解析 / 失败`。

### 3.4 搜索与筛选

- 搜索匹配 `Sxx`、手机号、ICCID、运营商。
- 状态筛选：全部、需充值、已过期、失败、尚未取得。
- 国家/运营商筛选在数据规模需要时增加；本期以搜索和状态为主。

## 4. 状态计算

充值阈值：

| 国家/地区 | 币种 | 阈值 |
| --- | --- | ---: |
| 中国大陆 | CNY | 100 |
| 新加坡 | SGD | 10 |
| 中国香港 | HKD | 100 |

余额健康状态按以下优先级计算：

1. 最近查询为 `failed` 或 `timed_out`：`查询失败`。若历史上已有余额，仍展示该金额，但状态保持失败。
2. 没有成功解析的现金余额：`尚未取得`。
3. 最近成功余额距今超过 35 天：`数据过期`。
4. 余额低于对应币种阈值：`需要充值`。
5. 其他情况：`正常`。

阈值无法匹配时不猜测，不标记低余额；状态可为正常，但阈值显示 `—`。后端增加运营商能力清单后，“尚未取得”应进一步拆分为“尚未查询”和“不支持自动查询”。

## 5. 查询详情与审计

复用现有余额查询详情层，展示：

- 当前解析余额和更新时间
- 按时间排序的发送/接收短信会话
- 其他解析指标
- 查询编号、运营商、查询方式、解析版本和发起时间
- 失败原因

概览和查询记录都打开同一详情层，避免产生两套审计展示。

## 6. 设备与卡边界

“设备与卡”只负责硬件、SIM 身份、运营商、信号和运行状态，不展示余额金额或余额状态。余额概览、查询入口和充值状态统一留在“余额”模块，避免两个页面对同一业务状态形成重复入口。

“设备与卡”和“余额”桌面表格均支持点击数据列的表头切换升序/降序；操作列不参与排序。未手动排序时，设备页保持异常优先，余额页保持需要处理的状态优先。

## 7. 数据与刷新

本期前端使用现有两个数据源：

- `/api/phones`：SIM 身份、卡号、号码、国家和运营商。
- `/api/balance-checks`：查询状态、会话和解析指标。

余额概览以 ICCID 合并数据。每张卡使用最近一次查询作为查询状态，使用最近一次包含 `cash_balance` 的成功记录作为当前余额。

当前加载最近 500 条查询记录，适合 95 卡每月一次的第一阶段。进入常态运行后应增加专用 `/api/balances` 概览接口，由后端返回每张卡的最新余额和最近查询，避免历史增长后受列表上限影响。

页面查询接口：

- `POST /api/balance-checks/query`：管理员触发单卡查询。
- `GET /api/balance-checks/query-preview`：管理员获取批量查询预览。
- `POST /api/balance-checks/query-batch`：管理员确认并由服务端批量入队。

守护进程原有的 `/api/control/balance-checks` 仍保留给受 `API_KEY` 保护的运维和自动化流程。

## 8. 充值能力边界

充值上线前必须具备：

- 独立、不可变的充值记录
- 操作权限与审批策略
- 幂等键，防止重复扣款
- 充值前后余额快照
- 运营商响应和失败原因审计
- 金额、币种和单卡/月度限额

满足以上条件后，余额模块增加“充值记录”和受权限控制的充值操作。本期不展示占位标签或失效按钮。

## 9. 本期验收标准

- 消息页三种内容筛选互不混淆。
- 余额页在桌面和手机均可使用，无横向溢出。
- S02 的 `264.33 CNY` 可在余额概览和查询详情中一致展示。
- 中国大陆、新加坡、香港阈值按币种正确计算。
- 最近失败、数据过期和无数据不会被误报为正常。
- 点击概览或记录可查看完整查询短信会话。
- 手机底部导航始终保留，余额页不使用悬浮卡片式页面边距。
- 自动化测试覆盖阈值、状态优先级和记录归并。

## 10. 实施阶段

1. 已完成：余额查询数据模型、多步短信会话、解析和详情展示。
2. 已完成：三段消息筛选、余额概览/记录和导航入口。
3. 已完成：管理员单卡触发、批量预览/触发、24 小时防重复和维护短信限流。
4. 后续：专用概览 API、按运营商扩展查询能力、每月调度和失败重试。
5. 最后：充值模型、权限、审批、幂等和运营商充值适配。
