# SMS Hardware Storage Baseline — 2026-08-14

## Scope and safety

This is the first Stage 0 evidence record for the
[SMS Hardware Storage Safety Plan](../../sms-hardware-storage-safety-plan.md).
It records existing behavior only. No daemon configuration, production database,
modem state, SMS deletion behavior, polling interval, or scheduled task was
changed while collecting it.

Repository baseline: `f073b72` (`main` working tree also contains documentation
and test changes for this assessment).

Production baseline is **not yet verified**. Two rounds of read-only SSH attempts
to both known Orange Pi addresses failed on 2026-08-14 (initial timeouts, then
connection-stage exit `255` with no remote output), so the deployed commit,
firmware responses, live logs, and seven-day metrics remain open evidence items.
Local routing was not changed and no production command completed.

## Code-level findings

| Area | Existing behavior | Evidence |
| --- | --- | --- |
| Physical stores | The AT reader discovers supported `mem1` stores and scans `ME`, then `SM`; `MT` is only a fallback. | `orange-pi-daemon/src/at_modem.rs:818-964` and parser/candidate tests at `:1973-2018` |
| Single-part durability boundary | A decoded message is inserted into local SQLite before an exact physical delete is attempted. | `orange-pi-daemon/src/main.rs:286-315` |
| Cloud upload ordering | Upload is asynchronous and occurs after local persistence and the initial physical-delete attempt. | `orange-pi-daemon/src/main.rs:367-459` |
| Failed physical delete | The failure is logged, but a later scan enters the local duplicate branch and does not retry deletion. | `orange-pi-daemon/src/main.rs:296-319`; deduplication at `message_store.rs:152-174` |
| Multipart messages | Each part is buffered locally with its store and index. Physical deletion is requested only after all parts assemble into a complete locally persisted message. | `orange-pi-daemon/src/modem_manager.rs:422-529` |
| Incomplete multipart expiry | The five-minute cleanup removes local segment rows only; it does not remove their physical `ME/SM` entries. | `orange-pi-daemon/src/main.rs:615-633`; `message_store.rs:786-802` |
| Physical occupancy | `AT+CPMS?` is available as a diagnostic, but `ME/SM used/total` is not continuously parsed and reported. | `orange-pi-daemon/src/at_modem.rs:788-789` |
| Operation serialization | `WorkerPool::processing` prevents overlapping reader cycles, and a semaphore limits reader workers. There is no unified per-modem lock shared by reading, storage selection, sending, diagnostics, and deletion. | `orange-pi-daemon/src/worker_pool.rs:69-125`; independent entry points in `modem_manager.rs:406-682` |

The missing unified per-modem lock is a Stage 1 design constraint. Observation
work must not add an independent `CPMS` store-switching task until a safe shared
serialization boundary is designed, reviewed, and explicitly approved.

## Regression contract

The existing tests cover `CPMS` store discovery, storage-aware physical paths,
local deduplication, SQLite upload states, multipart assembly, and segment cleanup.
Stage 0 adds explicit cases for:

- a physical path becoming eligible in the existing SQLite cleanup model only
  after the row is marked uploaded;
- a duplicate retaining only the first physical path, documenting why a separate
  deletion state is needed in a later stage; and
- incomplete multipart parts retaining their individual `ME/SM` locations.

A passing local test run does not substitute for production evidence.

## API-outage recovery reconciliation procedure

This procedure is read-only. It confirms that a locally durable received message
eventually exists in Cloudflare after API recovery.

1. On the Orange Pi, record aggregate local queue counts without selecting SMS
   bodies:

   ```sh
   sqlite3 /var/lib/sms-daemon/messages.db \
     "SELECT status, COUNT(*) FROM messages GROUP BY status ORDER BY status;"
   ```

2. Confirm uploader failures stop and a later successful batch appears in
   `sms-daemon` logs. Wait until the chosen row has local status `uploaded`.
3. Choose a received row from the outage window. In a private operator session,
   compare its full ICCID, timestamp, direction/type, and content against the D1
   `messages` row. Do not paste or commit either row. Record only:

   - masked ICCID (last four digits only);
   - timestamp and time zone;
   - SHA-256 of `ICCID + NUL + timestamp + NUL + content` on each side; and
   - whether the two hashes match.

4. Query Cloudflare D1 read-only using the exact ICCID and a narrow timestamp
   window. Retrieve the minimum fields needed to calculate the same hash. Store
   any temporary output outside the repository and delete it after comparison.
5. The reconciliation passes only when both hashes match and local queue counts
   show no unexpectedly stranded `pending`, `uploading`, or terminally failed
   row. A local `uploaded` state alone is not sufficient evidence.
6. Append aggregate counts and the hash-match result to a dated evidence record;
   never append SMS content, full phone numbers, full ICCIDs, API keys, or raw
   PDUs.
